# Baritone Helper 3.1 implementation specification

Status: approved by the user through the 3.1 proposed plan and the instruction to implement it.

## Product contract

The controller and dashboard remain the user interface. Starting a collection job must invoke the vendored Baritone `MineProcess` with the configured block targets, so discovery, target ordering, goals, path calculation, and movement behave like client Baritone's `#mine` operation. Work-area, protected-zone, ownership, and storage rules remain server-side constraints around that process.

Planning is server-authoritative. A living worker keeps a moving, player-style Chebyshev chunk radius of 12 (25 by 25 chunks) loaded even while idle or its owner is offline. The server's simulation-distance rules continue to determine which loaded chunks fully tick. Four active workers are the release performance target; additional workers must remain functional and fairly scheduled rather than being rejected.

## Failure model

| Failure | Required detector or defence |
|---|---|
| The old brute-force scanner remains on the production path | Contract test proves collection starts `MineProcess` and no controller call constructs `SearchCursor` |
| Target scanning blocks the server or examines absent palettes | Scanner tests assert nonblocking loaded-chunk access and palette rejection before block iteration |
| Baritone input arrives after physics or is overwritten by mob control | Movement GameTests record first-motion latency, forward/backward input, sprint, and stop behaviour |
| Async calculations race, ignore cancellation, or publish stale paths | Queue/cancel/goal-replacement stress tests and generation ownership assertions |
| Snapshot creation repeats every active tick | Instrumentation test limits snapshot creation to accepted calculations |
| Inventory changes are lost or duplicated between worker, hand, and Baritone | Conservation tests across tool swaps, durability, placement, buckets, and pickup |
| Remote inventory silently closes or permits unauthorized access | Owner same-dimension integration test plus non-owner and cross-dimension rejection tests |
| Network handlers mutate world/entity state off-thread | Handler test asserts server-thread execution |
| Chunk windows leak, shrink, or vanish across lifecycle transitions | Tests for 625 chunks, movement, idle, disconnect, restart, death, dismissal, and removal |
| Four workers starve the server or one another | Four-worker timing/fairness workload and JFR evidence |
| Existing 3.0 saves become unreadable | NBT and saved-data migration tests |

## Executable scenarios

1. **Dashboard target maps to `#mine`:** given a configured iron-ore target, starting the job activates `MineProcess.mine(0, targets)` and does not run `WorkerPlanner.SearchCursor` or manual stance routing.
2. **Loaded-world discovery:** given matching and nonmatching chunk sections inside the worker window, scanning returns Baritone's nearest/pruned target set, skips nonmatching palettes, and never loads a missing chunk synchronously.
3. **No known target:** given a fully ready window with no matching target, the worker stays paused and performs one coalesced periodic rescan without a cancel/restart loop or repeated cubic scan.
4. **Player-timed movement:** given a precomputed path, Baritone input is selected before travel, uses player-compatible directional magnitude and speed, preserves backward/strafe input, and stops on cancellation.
5. **Movement parity set:** straight, diagonal, ascend, descend, bridge, pillar, obstruction, parkour, and water fixtures produce the pinned client path/input trace, allowing at most one tick of arrival variance.
6. **Single canonical inventory:** swaps, tool damage, block placement, bucket exchange, drops, and deposits mutate worker storage exactly once and leave the selected hand equal to the selected canonical hotbar slot.
7. **Remote owner inventory:** an owner in the same dimension can open 27- and 54-slot inventories at any distance; a non-owner or owner in another dimension cannot.
8. **Player-style chunk window:** a spawned worker owns exactly the 25 by 25 view window around its current chunk, advances it when moving, retains it while idle and owner-offline, restores it after restart, and releases it after death/dismissal/removal.
9. **Fair bounded planning:** four workers can each own one running and one coalesced pending calculation; cancel-before-start, goal replacement, and worker removal prevent stale publication and release task ownership.
10. **Main-thread authority:** every dashboard action, worker state mutation, chunk-ticket mutation, and snapshot capture begins on the Minecraft server thread.
11. **Lifecycle idleness:** stop or completion disposes the Baritone engine and stops engine ticks while preserving the always-loaded chunk window; restart creates a clean engine.
12. **Performance:** after chunk warm-up, four workers sustain at least 19.5 TPS with p95 server ticks below 50 ms, aggregate worker orchestration at or below 2 ms p95, loaded 128-block calculations at or below 500 ms p95, and cancellation visibility within 100 ms.

## Negative constraints

- Do not add chat-command control or client-computed path payloads.
- Do not change Baritone movement costs, heuristics, movement graph, goal semantics, or target pruning except where the pinned client source already differs.
- Do not read live server chunks from planner threads.
- Do not impose a hard four-worker limit.
- Do not add runtime dependencies; use Java, NeoForge, and the existing Gradle/JUnit/GameTest toolchain.
- Do not publish a GitHub release as part of implementation.

## Verification setup

- Baseline and final commands: `gradlew test`, `gradlew runGameTestServer`, and `gradlew build` using the repository's Java 21 toolchain.
- Persist a fail-closed PowerShell gauntlet entry point and a manual mutation runner; add no new dependencies.
- Record source state, scenario-to-test mapping, skipped checks, benchmark/JFR results, and all failures in `EVIDENCE-3.1.md`.
- Git remains the restore/reference mechanism, but implementation does not create commits unless separately requested.
