# Baritone Helper 3.2 architecture

## Discovery ownership

Each worker still owns one relocated server-side Baritone engine. `MineProcess`
is the only component that chooses mining targets and exploration goals. The
worker controller owns job lifecycle and storage transitions; it does not run a
second search cursor or path planner.

`WORK_AREA` is the migration-safe default. It treats target coverage as finite
and may report exhaustion only after every eligible chunk is scanned. `ROAM` is
an explicit unbounded mode that expands through Baritone goals while retaining
no-enter, no-modify, storage, exclusion, and game-rule protections.

## Shared observations

World knowledge is attached to each server dimension through Minecraft
`SavedData`. Entries are keyed by target block and chunk and contain exact block
positions plus `UNKNOWN`, runtime `SCANNING`, `SCANNED`, or `DIRTY` coverage.
Interrupted scans restore as dirty. A chunk revision rejects results captured
before a block, fluid, piston, or explosion mutation.

Chunk palettes are copied on the server thread. Only immutable copies are read
by the bounded scanner executor, and publication returns to the server thread
after lifecycle-generation and chunk-revision checks. Shared observations never
contain work areas, zones, paths, blacklists, progress, or other worker policy.

Cached-world distance follows upstream Baritone's 512-block region contract;
packed locations are decoded as `BlockPos`, not `ChunkPos`.

Parity was re-audited against the official Cabaletta Baritone `1.21.1` branch at
`f3a51d47a05fa4fc9cacd6d90091f617a8d685df`. Its post-`5f259b7` change restores
reloadable server-registry loot resolution. This server-only derivative already
uses that registry source directly and intentionally omits the upstream client
level stub.

The current movement audit also keeps upstream's distinction between
`blocksToDisallowBreaking` (hard prohibition) and `blocksToAvoidBreaking`
(cost multiplier), source/flowing-liquid checks, powder snow and berry-bush
hazards, soul-sand and azalea supports, modern vines, pointed dripstone, and
amethyst clusters. Baritone Helper intentionally remains stricter at the
server boundary: block entities, work policy, `mobGriefing`, and no-modify
zones are always hard commit-time denials. A worker also retains a target
vertically sandwiched by bedrock long enough to distinguish a reachable side
from `SEARCH_AREA_UNREACHABLE`, while upstream prunes that candidate early.

## Runtime isolation

Path calculations and scans retain separate bounded executors (four and two
workers respectively). Active workers use a small sliding FULL view and a
separate simulation footprint. Stopped, blocked, completed, removed, and packed
workers release runtime tickets. Every path, scan, break, and pickup transition
has an explicit cancellation boundary; stale completion cannot revive it.

Planning and commit-time interaction checks are distinct. Entering checks own
path nodes and standing positions. Modification checks own break, placement,
fluid, storage, work-area, block-entity, exclusion, and `mobGriefing` rules.

## Packed lifecycle and protocol

Pickup is a server transaction, not an inventory dump. A versioned immutable
item component carries persistent worker identity, inventory, configuration,
progress, zones, storage, pathing settings, and activity. Runtime paths,
executor state, tickets, and active breaking are never packed. Transaction IDs
make delivery and restart reconciliation idempotent.

Protocol 4 addresses workers by UUID and dimension, retains optimistic-write
configuration revisions, and adds ordered runtime snapshots plus request replay
protection. Cross-dimension management is allowed; operations requiring the
player to interact physically with the worker's world remain explicitly
unavailable.

The dashboard remains one screen with Job, Area & Safety, Storage, Pathing, and
Activity tabs. All displayed search/path values come from immutable runtime
telemetry and full snapshots are rate-limited and equality-coalesced.
